## Current UX Tension

The current settings UI mixes two different product concepts under one area:

1. Native Transcriber summary
   - Generated by Transcriber.
   - Rendered inside the extension.
   - Could be bundled, metered, cached, persisted, and priced by Transcriber.

2. External AI handoff
   - Opens Claude or ChatGPT.
   - Uses the user's external account, limits, model, and context.
   - Transcriber does not control quality, cost, persistence, or long-input failures.

Because of this, copy such as `Open in` is misleading when the product is also offering native summary generation. Claude and ChatGPT are not just model choices for the same Transcriber summary product; they are handoff destinations.

## Decisions Needed Before Productizing

### 1. What is the primary product promise?

Recommended direction:

- Primary promise: `Transcribe & Summarize` creates both artifacts inside Transcriber.
- Claude and ChatGPT become secondary export or handoff actions.

Alternative:

- Treat Transcriber as a transcript router, where Claude/ChatGPT remain first-class summary destinations.

This decision controls Settings copy, pricing, onboarding, and the row actions in the Recent list.

### 2. How should the settings language change?

Current rough state:

- Button action: `Transcribe & Summarize`
- Provider row: `Open in Claude / ChatGPT`

Potential clearer split:

- `Summary output`
  - `Show in Transcriber`
  - `Open in Claude`
  - `Open in ChatGPT`

Or:

- Default action: `Transcriber summary`
- Secondary actions: `Open transcript in Claude`, `Open transcript in ChatGPT`

The second framing is cleaner because it avoids pretending Claude/ChatGPT are equivalent to Transcriber's native summary.

### 3. What is included for free?

Do not promise unlimited free summaries until cost and abuse data exist.

Possible starting point:

- Free: first transcript plus first native summary.
- Pro: included native summaries up to a fair-use cap.
- Self-hosted/local: local summarization can be unlimited when backed by user hardware or user-provided local model.
- External Claude/ChatGPT handoff: unlimited from Transcriber's perspective because the user pays through their own AI account.

### 4. What model is good enough?

The current native backend direction uses one platform-managed summary model. Before scaling, we need model quality and cost evaluation across real transcripts.

Minimum evaluation set:

- Short news/interview video.
- Long podcast.
- Technical tutorial.
- Business/copywriting video.
- Low-quality transcript or auto-captions.
- Dense multi-speaker discussion.

Evaluate:

- Summary usefulness.
- Factuality.
- Quote/timestamp quality.
- Token cost.
- Latency.
- Failure rate.

Candidate model families should include at least one very cheap model, one mid-tier model, and one high-quality baseline.

### 5. How should summaries be saved?

Short term:

- The extension can locally cache returned summaries for side-panel continuity.

Product-ready:

- Summaries should be first-class server artifacts.
- Cache key should include user, transcript, prompt hash, model, and summary schema/version.
- Duplicate YouTube links should reuse existing transcript and summary artifacts when allowed.
- The UI should show whether a summary is cached, refreshed, or generated with a newer model/prompt.

### 6. How do prompts and summary style work?

Open question:

- Do users configure a prompt, a style preset, or both?

Recommended first product version:

- Avoid raw prompt editing in the extension.
- Offer style presets later:
  - `Quick takeaways`
  - `Detailed notes`
  - `Action items`
  - `Research brief`

This aligns with `YTT-207` and `YTT-301`, but avoids turning first launch into prompt engineering UI.

### 7. How do note destinations use summaries?

The extension already exposes Notion and Obsidian. Future output modes should treat summary as a first-class artifact:

- Send transcript.
- Send summary.
- Send both.
- Per-destination default.

This maps to `YTT-213`.

## Suggested Next Sequence

1. Product decision: choose whether native Transcriber summary is the default promise.
2. UX copy pass: rename `Open in` and separate native summary from external handoff.
3. Cost instrumentation: revive or replace `YTT-215` before broad rollout.
4. Model eval: create a small fixed transcript set and compare cost/quality.
5. Persistence: make server summaries first-class artifacts, not only extension-local cache.
6. Pricing: define free and Pro summary limits from measured costs.
7. Destination integration: wire summary/transcript/both output modes.

## Merge Risk Notes

- This worktree is useful as a proof of product direction, but it should not be merged blindly as final UX.
- The native-summary extension depends on the cloud summary endpoint contract.
- Claude/ChatGPT handoff still matters for power users and for workflows where the summary should live inside an existing AI conversation.
- The product should avoid implying that Claude/ChatGPT summaries are free or controlled by Transcriber.
